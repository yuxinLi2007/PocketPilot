## 2. ESP32 是否支持 Android `GattWriteChunker` 的多片写入重组

### 2.1 结论

**支持。** ESP32 固件不把单次 GATT write 当作一条消息，而是把 TX 特征上的所有写入视为连续字节流，以 `\n` 作为逻辑帧边界，并在连接建立/断开时清空半帧缓冲。

Android 侧按 `MTU - 3` 切片顺序写入；ESP32 侧逐片追加，收到换行后一次性交给协议解析。因此一条 `COMMAND_TASK_TEXT` 被切成 26 片（MTU 23）后仍可被还原为完整一帧。

### 2.2 代码位置

| 环节 | 文件 | 位置 / 说明 |
| --- | --- | --- |
| Android 计算单片大小 | `android/app/src/main/java/com/pocketpilot/app/core/GattWriteChunker.java` | `payloadBytesForMtu()`：MTU 23 → 20 字节，MTU 185 → 182 字节，上限 512 |
| Android 切片 | 同上 | `split()`：按字节顺序切片，不改变 UTF-8 帧内容 |
| Android 发送 | `android/app/src/main/java/com/pocketpilot/app/transport/GattBleTransport.java` | `drainWrites()`（约 480 行）；仅上一片 `onCharacteristicWrite` 成功后发下一片（约 365 行） |
| ESP32 GATT 写入入口 | `firmware/pocketpilot_ble/main/pocketpilot_ble_main.c` | `ESP_GATTS_WRITE_EVT`（约 467 行） |
| ESP32 送入重组器 | 同上 | `pp_feed_rx_bytes()`（约 345 行），调用 `pp_rx_assembler_feed()` |
| ESP32 字节流重组 | `firmware/pocketpilot_ble/main/pp_rx_assembler.c` | `pp_rx_assembler_feed()`（约 18 行）：遇到 `\n` 交付一行；无换行则继续累积 |
| 超长帧丢弃 | 同上 | 缓冲达到 512 字节仍无换行时置 `discard=true`，丢弃到下一个换行后重新同步 |
| 连接生命周期清理 | `pocketpilot_ble_main.c` | 连接事件约 443 行、断开事件约 457 行调用 `pp_rx_assembler_reset()`；启动约 865 行初始化 |
| ESP32 结果帧校验 | `pocketpilot_ble_main.c` | `pp_handle_result_line()`（约 285 行）：校验版本、类型、命令 ID、状态 |

### 2.4 边界差异（已记录，未修改协议）

- Android 生产端上限：整帧含 `\n` 不超过 **512 字节**，即负载最多 **511 字节**。
- ESP32 重组器上限：换行前最多 **512 字节**，行缓冲为 513 字节（含结尾 NUL）。
- 因此 Android 不会发送 ESP32 无法接收的长度；ESP32 比 Android 多接受 1 字节负载。该差异是保守方向，暂不调整，避免改变现有协议语义。
- ESP32 **没有半帧超时**：半帧只在新连接/断连时清空；Android 接收方向有 2 秒半帧超时。这是两端当前的非对称行为，真实链路需重点观察。

## 3. Android 与 ESP32 协议对照

### 3.1 传输层

| 项目 | Android | ESP32 | 一致性 |
| --- | --- | --- | --- |
| 设备名 | 扫描 `PocketPilot` | 广播名 `PocketPilot` | 一致 |
| Service UUID | `6f706f63-6b65-742d-7069-6c6f74000001` | 同一 UUID（16 字节小端数组） | 一致 |
| RX 特征（设备→手机） | `...0002`，订阅 notify + CCCD `0x2902` | `...0002`，notify，带 CCCD | 一致 |
| TX 特征（手机→设备） | `...0003`，write | `...0003`，write | 一致 |
| 默认 MTU | 23 | 23 | 一致 |
| MTU 协商 | 尝试更大 MTU，失败回退默认值 | 接受协商并记录 `PP_MTU` | 逻辑一致，真实值未验证 |
| 消息边界 | `\n` | `\n` | 一致 |
| 文本编码 | UTF-8（严格解码） | UTF-8 字节流，不做字符转码 | 一致 |

### 3.2 消息类型与帧格式

| 类型 | 帧格式 | 字段说明 |
| --- | --- | --- |
| 固定命令 | `PP1\|COMMAND_OPEN_WECHAT\n` | 无参数 |
| 固定命令 | `PP1\|COMMAND_OPEN_MAP\|<address>\n` | 地址为 UTF-8，最多 120 个 Java 字符 |
| 固定命令 | `PP1\|COMMAND_BACK\n` | 无参数 |
| 任务文本 | `PP1\|COMMAND_TASK_TEXT\|<message_id>\|<utf8_byte_length>\|<text>\n` | `text` 放最后，可包含 `\|`；长度按 UTF-8 字节计算 |
| 执行结果 | `PP1\|RESULT\|<command_id>\|<STATUS>\|<detail>\n` | `detail` 中的 `\|` 替换为 `/`，换行替换为空格 |

| 字段 | 规则 |
| --- | --- |
| 协议版本 | 固定 `PP1`；其他版本拒绝 |
| 分隔符 | `\|` |
| 帧终止 | `\n`；帧内不允许额外 CR/LF |
| 整帧上限 | Android 512 字节（含换行）；ESP32 行缓冲 512 字节负载 |
| 任务文本上限 | 384 UTF-8 字节（发送端、接收端、Validator 三处校验） |
| message_id | 1–64 个 ASCII 字符，允许 `[A-Za-z0-9._:-]`，且非空 |
| 地图地址上限 | 120 个 Java 字符（`CommandValidator.MAX_ARGUMENT_LENGTH`） |
| 结果 detail | 发送前按 UTF-8 字节预算截断，不切断多字节字符 |

### 3.3 ACK / RESULT

| 项目 | 行为 |
| --- | --- |
| 业务 ACK 帧 | **不存在**。协议没有单独的 `ACK` 消息类型 |
| ATT write response | ESP32 在 `need_rsp` 时回 `ESP_GATT_OK`（约 486 行）；这只表示链路层写入被接受，**不代表手机动作成功** |
| Mock 回执 | `FakeBleTransport` 的 `TargetAckReceiver` 是 Android 本地测试替身，不是 ESP32 真实回执 |
| 执行结果 | Android 执行后发送 `PP1\|RESULT\|...`；ESP32 校验并记录 `PP_RX_RESULT` |
| RESULT 计数 | 仅合法 RESULT 增加 `results_ok`；非法帧增加 `rx_rejects` |

`STATUS` 取值（两端一致）：

| STATUS | 含义 |
| --- | --- |
| `RECEIVED` | 命令已接收，尚未执行完成 |
| `REJECTED` | 命令或任务被拒绝 |
| `NOT_INSTALLED` | 目标应用未安装或不可启动 |
| `PERMISSION_REQUIRED` | 缺少必要授权 |
| `EXECUTED_UNCONFIRMED` | 已尝试执行，但无法确认结果 |
| `CONFIRMED` | 有可获得的证据确认执行成功 |
| `FAILED` | 执行失败 |

### 3.4 非法帧处理

| 场景 | Android 接收设备帧 | ESP32 接收手机 RESULT |
| --- | --- | --- |
| 空帧 / 空行 | `EMPTY_FRAME` | `EMPTY_FRAME` |
| 超过 512 字节 | `FRAME_TOO_LONG` | `FRAME_TOO_LONG` |
| 非法 UTF-8 | `INVALID_UTF8` | 按原始字节处理，遇到非法字段即拒绝 |
| 缺少分隔符 / 字段不完整 | `MALFORMED_FRAME` | `MALFORMED_FRAME` |
| 协议版本不是 `PP1` | `UNSUPPORTED_VERSION` | `UNSUPPORTED_VERSION` |
| 未知命令类型 | `UNKNOWN_COMMAND` | `UNSUPPORTED_FRAME_TYPE`（非 RESULT） |
| 未知 RESULT 命令 ID | 不适用（Android 产生结果） | `UNKNOWN_COMMAND`；允许 `PROTOCOL-*` 与合法 message_id |
| 未知 STATUS | 不适用 | `UNKNOWN_STATUS` |
| 任务文本为空 | `EMPTY_TASK_TEXT` | 不适用 |
| 声明长度非十进制 / 超上限 / 不匹配 | `INVALID_LENGTH` / `TEXT_TOO_LONG` / `LENGTH_MISMATCH` | 不适用 |
| message_id 非法 | `INVALID_MESSAGE_ID` | 不适用 |
| 半帧超时 | 2 秒后丢弃，产生 `FRAME_TIMEOUT` 状态错误 | 无半帧超时，仅连接/断开时清空 |
| 超长后的字节流 | 丢弃到下一个换行并重新同步 | 丢弃到下一个换行并重新同步 |
| 重复固定命令 | `CommandValidator` 300 ms 窗口内标记 duplicate | 不适用 |
| 重复任务 message_id | `TaskMessageGuard` 60 秒 TTL、容量 64 去重 | 不适用 |
| Planner 拒绝的任务 | 保持 `BLOCKED/REJECTED`，不产生动作 | 仅记录对应 RESULT |

## 6. 长帧处理

- Android 写入分片：`GattWriteChunker`，按 `MTU-3` 计算；MTU 23 → 20 字节/片，MTU 185 → 182 字节/片，上限 512。
- `GattBleTransport` 仅在上一片 `onCharacteristicWrite` 成功后发送下一片；断连/失败清空在途帧。
- 协议自测：511 字节 RESULT 帧按 20 字节切分为 26 片，逐片拼回与原帧字节一致；中文字符跨片仍可重组。
- ESP32 接收：已由主机测试验证 26 片重组、512 字节边界、513 字节拒绝、超长后重新同步。
- **真实 BLE 链路上的长帧可靠性尚未验证**，尤其是 MTU 23 下多片写入的时序、ATT 响应和 ESP32 通知发送。
