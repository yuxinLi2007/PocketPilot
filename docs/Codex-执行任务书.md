### T0 Go 条件（必须同时满足）

1. `unlocked` 下至少 **4 条**媒体键"通过"（≥9/10 成功，中位延迟 ≤300 ms）；
2. `locked_background_music` 下播放/暂停 + 音量 ± 至少 **2 条**"通过"；
3. 全程 `status≠0` 为 **0**，且没有"必须拔电才能恢复"的死机。

### 三条一票否决

- 高风险动作未经确认被执行 = **0 次**；
- 全局停止从触发到中断 ≤ **300 ms**；
- 拿不出原始测试记录（CSV/日志），只有口头描述。

## 2. 任务卡（可直接复制给 Codex）

### 任务 0：T0 数据回收与判定（用户测完后执行）

```
【任务】在仓库根目录读取 T0-平台通道穿刺记录表.csv、T0-配对与重连记录表.csv 和 firmware/t0_hid_probe/artifacts/logs/ 下串口日志，做 T0 判定。

【执行方式】
优先跑脚本，不要手算：
  cd <仓库根目录>
  python tools\t0_selftest.py      # 先确认判定规则本身没坏，应输出 7/7 通过
  python tools\t0_evaluate.py      # 生成 docs\T0-GoNoGo-报告.md，控制台打印结论

【要求】
1. 先看报告第 1 节"数据完整性"：缺什么就列什么，不要猜、不要补。
2. 结论只有三种：Go / No-Go / 数据不足；脚本给出的结论不得人工改写。
3. 人工只做两件事：核对脚本引用的日志确实是本次测试的、把失败现象翻译成人话。
4. 结论为 No-Go 时，按报告第 7 节的失败模式写 T0.5 修复计划；为 Go 时冻结 T0。
5. 不要改固件，不要改 CSV 原始数据，不要编造缺失值。
```

### 任务 1：T0.5 失败修复（仅当 T0 未通过）

```
【任务】基于 docs/T0-GoNoGo-报告.md 的失败模式，修 T0 固件。先诊断，后改代码。

【约束】
1. 先列出最可能的 3 个原因（报告描述符 / 连接参数 / 重连与绑定 / 电源），给判断依据。
2. 一次只改一个变量；每次改动前保存原日志，改动后重新烧录并复测同一组用例。
3. build.ps1 / flash.ps1 必须仍可用；产物 SHA 写入 BUILD-INFO.txt。
4. 不许用"应该修好了"结案，必须有 before/after 数据。
5. 输出 docs/T0.5-修复记录.md：假设 / 改动 / 证据 / 结果 / 是否回滚。
```

### 任务 2：L1 语音方案调研（只调研，不写代码）

```
【任务】调研在 ESP32-S3-EYE 上做中文离线命令词识别的可行方案，输出 ADR-002。

【必须回答】
1. ESP-SR 在 ESP32-S3（8MB Flash / 8MB PSRAM）上支持哪些 WakeNet / MultiNet 模型？中文命令词上限多少？
2. 单麦克风、近场（≤50cm）条件下的已知限制；官方给的延迟/内存数据与测试条件。
3. 10 条候选命令（含 6 个媒体键 + 4 个备选），每条给触发词、冲突词、失败后果。
4. 与"按键触发 + 云端识别"对比：离线方案在准确率、延迟、隐私、成本上的取舍。
5. 结论：能做 / 勉强能做 / 做不了，逐条给官方文档链接。

【禁止】写固件代码；给没有来源的性能数字；把"可能"写成"可以"。
【输出】docs/adr/ADR-002-离线语音方案.md，含来源清单与"什么情况下推翻"。
```

### 任务 3：L1 固件最小实现

```
【任务】按 ADR-002 实现 L1 固件：按键触发 → 离线识别 → BLE HID 发媒体键。

【范围】
1. 只做 10 条命令，只映射到现有 6 个 Consumer 报告；不碰安卓 App、不碰云。
2. 状态机：IDLE → LISTENING → RECOGNIZING → SENDING → IDLE；每步有串口日志。
3. 识别失败/超时：屏幕给出明确反馈，不发送任何键；连续失败 3 次回到 IDLE。
4. 保留现有 T0 串口命令，便于回归测试；新增命令不得破坏旧命令。
5. 屏幕显示：当前状态、识别结果、最近一次动作。

【验收】build.ps1 一键构建；flash.ps1 一键烧录；给出 10 条命令的逐条自测记录。
【禁止】改 HID 报告描述符（除非有 T0.5 的明确结论）；加语音播报（板子没有喇叭）。
```

### 任务 4：L1 测试与调优

```
【任务】对 L1 固件做识别与端到端测试，输出可复核的数据。

【测试】
1. 安静环境：10 条命令 × 10 次 = 100 次；记录识别结果、是否正确执行、延迟。
2. 噪声环境（约 55 dB，手机放白噪/人声底噪）：同样 100 次。
3. 端到端延迟：从"说完"到"手机动作开始"，至少 30 个样本，给中位数与 P90。
4. 错误执行：识别成另一条合法命令并执行的次数，单列；危险命令必须为 0。

【输出】results/L1-识别测试.csv + docs/L1-测试报告.md（结论、失败样本、调参建议）。
【约束】不达标先调参/换模型，不先换硬件；每次调参记录版本与数据。
```

### 任务 5：L2 安卓方案 ADR（只调研，不写 App）

```
【任务】输出 L2 安卓执行层的两份 ADR：ADR-003 无障碍与安全执行、ADR-004 BLE GATT 协议。

【必须回答】
1. 无障碍服务在主流国产 ROM 上的可用性、被系统回收/限制的典型情况、降级方案。
2. 用 AccessibilityService 能做/不能做的动作清单（返回、主页、打开 App、点击、读文本、拨号）。
3. 高风险动作清单：发送、拨号、付款、删除、改权限——每类的确认页与超时策略。
4. 全局停止怎么做到 ≤300 ms：本地停止位、执行前二次检查、网络卡住时的兜底。
5. GATT 协议：报文格式、字段、校验、幂等键、超时、重连、版本兼容。
6. Google Play 对无障碍服务用途的政策风险；不上架的内部分发路径。

【禁止】写 App 代码；承诺"支持所有 App"；忽略国产 ROM 差异。
【输出】docs/adr/ADR-003-安卓执行层.md、docs/adr/ADR-004-BLE-GATT协议.md。
```

### 任务 6：L2 App 最小实现（只做三条）

```
【任务】实现安卓 App 的最小闭环：BLE GATT 收命令 → 无障碍执行 → 确认页 → 全局停止 → 日志。

【范围】
1. 只做 A3 返回、A4 回主页、A9 全局停止；不做打开 App、不做拨号、不做付款。
2. 确认页只对"高风险动作"出现；L1 的三条命令不弹确认，但要有可见状态。
3. 全局停止必须在任何执行状态下有效；用本地标志位，不依赖网络。
4. 日志：时间、命令、执行结果、耗时、失败原因；默认不截屏、不存音频。
5. 提供 debug APK 与 adb 安装/卸载说明；不需要上架。

【验收】三条场景各连续 3 次成功；停止测试 10 次全部 ≤300 ms；日志可追溯。
【禁止】申请无关权限；把无障碍当"万能点击器"；在未经确认时执行高风险动作。
```

### 任务 8：L3 AI 单任务闭环（只做一个任务）

```
【任务】实现"从可访问的消息里取地址 → 打开地图 → 搜索 → 验证结果"的单任务闭环。

【范围】
1. 只做一个任务，不做通用 Agent，不做多 App 编排。
2. 服务部署在局域网；输入优先用无障碍树文本，截图只作兜底。
3. 成功条件必须可验证：地图页出现目标地址/搜索结果，而不是"看起来打开了"。
4. 失败恢复：地址不唯一 → 让用户选；地图未安装 → 明确提示；超时 → 停止并回退。
5. 全链路日志：理解结果、执行步骤、验证结果、总耗时。

【验收】10 次测试，成功 ≥8 次；失败必须可解释、可恢复；总耗时中位数 ≤15 s。
【禁止】把网页/消息里的文字当指令执行（防提示注入）；保存完整音频/截图。
```

### 任务 9：产品验证（5 人）

```
【任务】设计并执行 5 人试用，回答"这个产品值不值得继续做"。

【步骤】
1. 选 5 个目标用户（同一类人群，不要混），每人 30 分钟。

【输出】docs/P-产品验证报告.md：数据表、3 条洞察、继续/停止建议。
【判定】≥3 人表示"特定场景下比手动快 30% 以上且愿意继续用"才算有继续价值。
```

## 4. 红线（写进每个任务的开头）

1. **先调研再动手**：不确定的硬件参数、SDK 行为、系统权限，先查官方文档并列出出处。
2. **小步交付**：每完成一个可独立验证的小块就停下来汇报，不一次性写完整套系统。
3. **不许编造**：没有实机验证的一律写"未验证"；没有来源的数字不写。
4. **不跳 Gate**：T0 未过不做 L1；L1 未过不做 L2；L2 未过不做 L3。
5. **不扩范围**：L1 只做媒体键；L2 先做三条；L3 只做一个任务。
6. **安全优先**：高风险动作必须确认；全局停止必须可用；默认不存音频/截图。
7. **可复现**：每条结论能追溯到文档或日志；每个构建能一条命令重来。
