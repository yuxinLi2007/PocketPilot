## 1. 一句话产品定位

**PocketPilot 是吸在老人手机背面的实体语音按键——按住说一句话，手机就把事办了。**

## 2. 30 秒介绍（电梯版）

"爸妈不会用智能手机，不是他们笨，是手机不是为他们设计的。PocketPilot 是一块吸在手机背面的小薄板，上面有一个大主键、两个小预设键。按住大键说'打开微信'，手机就打开微信——这几句常用话离线就能识别，不用联网。按住预设键，手机跳到拨号盘、女儿号码已经填好，按一下绿色键就打出去。不用喊唤醒词，说错了也不会乱来——支付转账类操作我们从产品定义上就不存在。设备端链路已在开发板真机上验证，手机端已经在模拟器上跑通，整机端到端正在联调。"

## 3. 1 分钟介绍（路演版）

"老年群体规模数以亿计，他们使用智能手机时最大的障碍不是看不见，而是'找不到、记不住、不敢按'（**这是我们的需求假设，尚无问卷数据支撑，正在补 5-10 位老人访谈**）。现有方案都有硬伤：语音助手要喊唤醒词、离线能力只在旗舰机；智能音箱出不了门；老人机没有微信。

PocketPilot 的思路是把交互压缩到一个动作：**按住，说话，松手**。设备在本地把语音识别成命令——这里要说明白：它只听得懂**事先注册过的几句固定说法**（打开微信、打开地图、返回），不是通用语音助手，听不懂的话会礼貌拒识——识别完成后通过蓝牙让手机执行，结果用语音播报。首批支持这三个命令，外加子女远程配置的预设拨号键：按住它，手机跳到拨号盘、号码已填好，按一下绿色键拨出。

安全是底线设计：财产类操作在命令词、通信协议、执行器五个层面物理性不存在，防线经过 120 项自动化回归测试。目前设备端链路已在开发板真机闭环，手机端已在模拟器闭环，下一步是真实手机的端到端联调。"

## 4. 申报书/PPT 首页正式介绍

> **PocketPilot——面向老年群体的实体语音交互终端**
>
> 本项目针对老年群体使用智能手机时"找不到图标、记不住流程、畏惧误操作"的核心障碍，设计并实现了一种"实体按键 + 离线语音识别 + 受约束执行"的手机辅助交互系统。系统由磁吸式硬件终端（ESP32-S3，按键/麦克风/蓝牙）与 Android 配套应用组成：用户按住按键说出指令，终端在本地完成中文命令词识别（无需网络与唤醒词），经 BLE 协议传输至手机，由应用层在"白名单动作 + 权限校验 + 结果核验"的三重约束下执行并反馈。项目独创六层财产安全防守体系，从产品定义上排除支付转账类能力，通过 120 项自动化回归测试验证。当前已完成设备端全链路真机验证与手机端模拟器验证，正在推进端到端真机联调与老年用户可用性实测。

## 5. 核心痛点与解决方案（**痛点均为需求假设，待访谈与实测验证**）

| 痛点（假设） | 现有方案为什么不行 | PocketPilot 的解法 |
|-|-|-|
| 找不到图标、记不住步骤 | 老人模式只是图标变大，步数没少 | 一个动作：按住说话 |
| 怕按错、怕扣钱 | 语音助手功能越全越危险 | 白名单默认拒绝；支付能力物理不存在 |
| 看不清、听不清反馈 | 执行结果只显示在屏幕上 | 手机语音播报 + 按键灯语 + 震动三重反馈 |
| 子女不在身边没法教 | 远程指导靠电话，效率极低 | 子女 App 一次配置预设键，异常自动推送子女 |

## 6. 核心功能介绍

1. **按住说话**（主键）：打开微信 / 打开地图 / 返回上一页——设备端离线命令词识别，只认这几句注册说法 🔵 设备端已实现（真机 3/3，单样本）／🟡 整机端到端待打通；
2. **预设键 ×2**（子女配置）：长按 = 打开拨号盘并预填号码 / 导航回家，号码只存在 App 里，不进协议帧、不进日志；**拨出前保留用户一次确认，不自动拨打** 🔴 开发中（COMMAND_DIAL）；
3. **状态三重反馈**：按键透光（绿=成功/红闪=失败）+ 手机语音播报 + 震动 🔴 硬件件未打样，播报链路随端到端验证；
4. **异常有出路**：没听清会教老人标准说法；手机没装 App 会播报；断连自动重连并通知子女 🟡 播报与拒识提示待真机；🔴 子女推送开发中；
5. **安全红线**：任何版本不做支付、转账、发消息、读屏幕——六层防守，自动化回归随每次迭代验证 🔵 已实现（纯 Java 回归 120/0）。

## 7. 整体技术架构

```
老人按住说话
   │
   ▼
┌────────────┐  离线命令词识别（ESP-SR）
│  硬件终端   │  ──────────────────────► 识别为命令
│ 按键/麦克风 │◄────── 灯/震反馈 ──────┐
└─────┬──────┘                        │
      │ BLE（JSON 帧 / 幂等去重 / 六态回执）
      ▼                               │
┌────────────┐   白名单校验            │
│ Android App│ ──► 标准 Intent / 受限无障碍 ──► 手机执行
│  校验/执行  │ ◄── 结果核验（区分"执行了"与"确认了"）
└────────────┘ ──► TTS 语音播报结果 ──────────┘
```

三条设计铁律：① AI 理解 ≠ 能执行，执行必须过白名单；② L2/L3 智能层 800ms 超时自动回退到规则层，智能永不拖慢可靠；③ 财产安全六层防守，拦截逻辑故障时按"拒绝"处理（fail-safe）。

## 8. 硬件架构

| 模块 | 原型（已验证） | 商业化目标（规划中） |
|-|-|-|
| 主控 | ESP32-S3-EYE 开发板 | ESP32-S3-PICO-1 SiP（同家族，固件零改动迁移） |
| 语音 | 板载 I2S 数字麦 + ESP-SR 离线命令词 | MEMS 麦 + 侧向短声道（薄机身补偿，待实测） |
| 通信 | BLE GATT（MTU 185，分片重组 12/0 通过） | 同协议 + 配对绑定加密（已列入补强） |
| 电源 | USB 供电 | 250-300mAh 薄锂电 + 深度睡眠（续航目标 ≥5 天，待实测） |
| 结构 | — | 68×56×5.5mm 圆角薄板，铝正面盖 + 塑料背壳（天线侧），磁吸 ≥3N |
| 交互 | BOOT 手势键（5/5 实测） | 凹槽内嵌苔绿主键 + 2 预设键，物理防误触 |

## 9. 软件及 AI 工作流程

1. 设备端：按键触发 → 麦克风采集 → ESP-SR 命令词识别（约 2.1-2.9 秒实测）→ 组装 JSON 命令帧（含唯一 ID）→ BLE 分片发送；
2. 手机端：字节流重组 → 命令校验（白名单/参数/财产守卫）→ 规则规划器匹配动作 → 执行器执行（Intent 或受限无障碍）→ 结果核验 → 六态回执回传 + TTS 播报；
3. 安全链：所有规划输出必经 FinancialGuard（60+ 财产关键词 + 金额模式 + 防全角/空格绕过），拦截码 `FINANCIAL_CONTENT_DENY`，守卫自身异常按拒绝处理；
4. 可观测：执行记录 JSONL 落盘，Lab 监测站实时展示命令级成功率、耗时分布与安全拦截次数。

## 10. 创新点与差异化

1. **交互创新**：零唤醒 + 离线 + 实体键三位一体，把语音交互压缩到一个动作（可被现场演示验证，非概念包装）；
2. **架构创新**："受约束的手机 Agent"——不追求 AI 万能，追求在窄边界内 100% 可靠；三层智能带 800ms 硬回退；
3. **安全创新**：财产能力"物理性不存在"的五层冗余设计 + 文本层守卫，配合 120 项回归测试，是同类适老产品中少见的工程化安全实践；
4. **工程诚实度**：全仓库"已验证/待验证"分级标注，模拟器数据与真机数据严格分离——这本身是方法创新。

## 11. MVP 与商业化产品的区别

| | MVP（当前原型） | 商业化产品（目标） |
|-|-|-|
| 硬件 | ESP32-S3-EYE 开发板，USB 供电 | 自研 68×56×5.5mm 薄板，电池供电，磁吸 |
| 功能 | 3 命令 + 预设拨号（开发中） | + 词表扩充、三重自检、BLE 加密、深度睡眠 |
| 验证水平 | 设备真机/手机模拟器分别闭环 | 端到端真机 + 老人实测 + 手板 OTA/续航实测 |
| 生产 | 无 | 3D 手板 → 小批量 → 开模（4-10 万沉没成本，验证卖动才投） |
| 认证 | 不需要 | SRRC + CCC + BQB（发布前 4 个月启动） |

**一句话：MVP 验证"这条路通不通"，商业化验证"值不值得走"。两者用的芯片同族、协议相同，迁移成本已被选型决策最小化。**

## 12. 技术可行性分析

- **已闭环（有测试记录）**：设备端按键→识别→蓝牙发送（真机）；协议栈/规划器/执行器/财产防线（模拟器与纯 Java 回归，累计 200+ 项 PASS）；
- **理论可行、待实测**：真机端到端（双端代码就绪，测试清单已备）；薄机身声学、铝盖天线、续航（方案与验收门槛已定义）；
- **明确不做**：通用 AI 助手、支付能力、读屏——主动收窄边界换取可靠性；
- **结论**：本项目没有需要"突破性技术"才能解决的环节，全部是成熟技术的正确组合与工程纪律问题。可行性风险集中在"真机环境差异"与"老人真实可用性"两处，均有对应验证计划。
