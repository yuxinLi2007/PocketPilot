## 💡 为什么要做 PocketPilot？

手机功能越来越多，但完成一件小事，有时仍然需要经过多个页面、按钮和确认步骤。

例如：

- 想打开某个应用，却要先解锁手机，再寻找图标；
- 想把刚收到的地址打开地图，需要在消息和地图之间来回切换；
- 想给家人发一条固定内容的消息，需要重复执行相似的操作；
- 想让手机完成多个步骤，却发现传统语音命令往往只适合明确、简单的指令。

手机语音助手已经很强大，PocketPilot **不打算重新造一个语音助手**，也不把“能用语音打开应用”当成创新。

我们想探索另一种交互方式：

**用一个随手可触及的实体入口，把常用指令做得更快，把多步骤任务做得更可靠，并让用户能够复用自己确认过的操作流程。**

<div align="center">

| 传统操作 | PocketPilot 的目标体验 |
|:---:|:---:|
| 解锁 → 找应用 → 逐步点击 | 按键 → 说出需求 |
| 每次重复相似操作 | 将常用流程保存为快捷指令 |
| 执行后不一定知道是否成功 | 检查关键步骤与最终状态 |
| 复杂任务需要用户自己切换应用 | 由 AI 拆解任务，逐步执行与核验 |

</div>

*以上为目标体验示意，具体能力以实际实现和测试结果为准。*

## 🧭 核心理念

PocketPilot 采用 **“本地快指令 + AI 复杂任务”** 的双通道设计。

### ⚡ 通道一：本地快速指令

针对高频、明确、可预期的操作，优先使用设备端的离线命令识别和预先配置的动作映射。

例如：

- “返回上一页”
- “打开微信”
- “打开地图”

这类命令不需要每次都请求云端大模型。目标是减少网络依赖和不必要的推理等待。

### 🧠 通道二：AI 多步骤任务

面对需要理解上下文、提取信息或跨应用操作的需求，再由 AI 参与任务规划。

例如：

- “把刚收到的地址打开地图。”
- “给张三写一条消息，说我已经到了。”

系统将尝试把目标拆成可检查的步骤，并在关键节点核验执行结果。涉及发送消息、付款、删除等敏感操作时，应在执行前让用户确认。

> **设计原则：简单任务走快路，复杂任务有规划，关键操作可确认，执行结果可验证。**

## 🎬 产品体验

### 场景一：一句话，完成常用操作

<p align="center">
  <img src="docs/images/quick-command-flow.png" alt="快速指令流程示意：按下实体按键、说出指令、设备识别并触发手机动作" width="90%">
</p>

1. 用户按下 PocketPilot 实体按键。
2. 说出预设的常用指令。
3. ESP32-S3-EYE 在本地识别支持的命令。
4. 通过蓝牙低功耗等通信方式，将指令发送给 Android 配套应用。
5. 手机执行已配置的动作，并反馈执行状态。

**目标：** 对高频操作减少不必要的云端调用，让响应更直接。

### 场景二：让 AI 处理多步骤需求

<p align="center">
  <img src="docs/images/ai-task-flow.png" alt="AI 任务流程示意：语音输入、任务拆解、手机执行、状态核验" width="90%">
</p>

以“把刚收到的地址打开地图”为例：

1. 获取用户授权范围内的相关消息或文本。
2. 提取其中的地址，并在不确定时询问用户。
3. 调用手机端允许使用的操作接口打开地图。
4. 检查地图是否成功打开，以及目标地址是否正确。
5. 若执行失败，提示原因并提供恢复选择。

复杂任务的执行时间取决于语音识别、手机接口、网络与模型推理，不承诺所有操作都能即时完成。

### 场景三：把自己的习惯变成快捷流程

<p align="center">
  <img src="docs/images/personal-shortcuts.png" alt="个人快捷流程示意：用户为常用语句配置动作并保存为可复用流程" width="90%">
</p>

用户可以为高频需求配置自己的触发语句与操作流程。例如，将“我准备出门了”映射到一组经过用户确认的动作。

系统记录流程的成功与失败，帮助用户发现哪些步骤稳定、哪些步骤需要调整。**保存的是明确、可复用的操作流程，而不是让 AI 不受约束地自动学习并执行所有行为。**

## 🧰 功能规划

| 功能 | 说明 | 规划阶段 |
|---|---|---|
| 实体按键触发 | 通过物理按键开始收音或触发命令 | 原型基础 |
| 本地语音命令 | 识别少量预设中文指令 | 首版目标 |
| 蓝牙指令传输 | 将指令发送给 Android 配套应用 | 首版目标 |
| Android 快捷操作 | 执行经授权的系统动作或应用启动 | 首版目标 |
| AI 自然语言理解 | 将复杂表达转换为结构化任务 | 后续接入 |
| 多步骤任务编排 | 按步骤执行，并检查关键状态 | 后续接入 |
| 用户快捷流程 | 保存、修改和复用常用操作 | 后续接入 |
| 执行记录与恢复 | 记录成功、失败及可恢复步骤 | 后续接入 |
| 摄像头辅助理解 | 作为补充输入方式探索 | 可选扩展 |

**说明：** 表格描述的是开发规划，不代表上述功能已经全部实现。项目会优先验证最小闭环，再逐步增加能力。

### 各部分的职责

**ESP32-S3-EYE：实体交互与本地快指令**

- 接收实体按键事件；
- 采集语音；
- 识别有限的预设命令；
- 通过屏幕反馈工作状态；
- 通过蓝牙低功耗或无线网络发送指令。

**Android 配套应用：手机操作执行端**

- 接收并验证来自设备的命令；
- 通过允许使用的系统接口执行动作；
- 在用户明确授权的前提下使用无障碍能力；
- 管理联系人映射、快捷流程和权限；
- 将执行结果反馈给任务服务。

**AI 任务服务：复杂任务理解与规划**

- 理解自然语言目标；
- 将目标转换为受约束的任务步骤；
- 根据执行反馈决定继续、重试或询问用户；
- 保存经用户同意的快捷流程与必要的执行记录。

### 为什么不直接把大模型放进开发板？

ESP32-S3-EYE 适合轻量级语音命令、实体交互和设备控制，但不适合独立运行完整的大型语言模型。

因此，PocketPilot 不要求所有 AI 能力都运行在设备端：

- 高频固定指令尽量本地处理；
- 手机控制由配套应用完成；
- 复杂语义理解与任务规划由电脑端或云端服务承担。

未来更换更强的主控芯片时，手机操作与任务服务可以继续复用。

## 🧪 为什么选择 ESP32-S3-EYE？

<p align="center">
  <img src="docs/images/esp32-s3-eye-board.png" alt="ESP32-S3-EYE 开发板实物图，请替换为自己的开发板照片" width="70%">
</p>

ESP32-S3-EYE 为早期原型提供了实体设备所需的基础能力：

- **实体按键：** 适合设计一按开始、重复指令和求助等交互；
- **数字麦克风：** 可用于语音输入；
- **小尺寸显示屏：** 显示待机、识别中、执行中、成功或失败等状态；
- **无线通信：** 与手机或电脑服务交换指令和状态；
- **摄像头：** 可用于后续探索视觉辅助交互。

本项目首版不会要求开发板独立承担复杂视觉推理，也不会把摄像头识别手机屏幕作为唯一控制方式。能否访问某个应用或执行某项操作，取决于 Android 系统接口、用户授权和具体应用的限制。

## ✨ 创新点与差异化

PocketPilot 不把“语音控制手机”本身当作创新，而是尝试把以下能力组合成一个更实用的交互产品。

### 01 · 快慢分流

高频、确定的命令优先本地执行；开放式、复杂的需求再交给 AI 规划，减少所有请求都依赖大模型的情况。

### 02 · 从一句指令到可检查的任务流程

复杂需求被拆成多个步骤。系统不仅尝试执行，还要检查关键结果，避免只根据模型生成的文字就宣称任务成功。

### 03 · 个人快捷流程

允许用户将常用需求配置成可复用流程，并根据执行记录优化流程，而不是每次都从头描述。

### 04 · 实体交互入口

实体按键提供明确的触发方式，用户无需每次先找到并打开一个专门的应用。实体设备是否比纯软件更方便，需要通过实际测试验证。

### 05 · 以授权和确认作为默认设计

设备只执行配套应用被授权的操作；发送消息、付款、删除等高风险动作应设置确认机制。用户可以查看、修改或删除已保存的快捷流程。

## 🔐 安全与隐私

手机操作涉及联系人、消息和个人信息。PocketPilot 将遵循以下原则：

- **明确授权：** 由用户决定配套应用可以访问哪些能力；
- **敏感操作确认：** 对发送消息、付款、删除等操作设置确认步骤；
- **最小化数据：** 本地快指令不必上传云端，复杂任务只传递必要信息；
- **可查看、可撤销：** 用户能够查看和删除已保存的快捷流程及记录；
- **不伪造成功状态：** 无法确认执行结果时，应明确提示“尚未确认”，而不是宣称任务已完成。

本项目不会尝试绕过手机系统权限，也不承诺能够控制所有应用或所有系统设置。
